## 3. Blocking questions

1. Does "Fastest first" really put `BuildPosition` first and hand the user a blocked ordering — intended teaching moment, or a bug I would be demoing?
2. If I edit `dsl/catalog.go` and restart the worker with runs in flight, is anything expected to survive, or is this demo assumed single-shot?
3. Are the seven figures in the ordering table from the current seed, or carried over from one of the earlier scenarios?

## 4. Cross-SDK

Almost all of it carries — by-name dispatch, a data bag, per-step activity options are idiomatic in Java/TypeScript/Python too; the one thing I could not carry is the retry/timeout and catalog-versioning story, because the README never states it in any SDK.

## 5. Verdict

- Explain the DSL idea to a customer: **yes** — the requires/optional/ordering argument lands on one read.
- Decide whether a customer needs it: **partly** — no cost, no "when not to", no durability rationale.
- Write one myself: **partly** — timeout kind, retry policy, and catalog-change safety are all unstated.
- Demo this repo from these docs: **no** — the Fastest-first claim and the `/api/plan` curl output are both wrong.
