Dynamic dispatch

Steps are scheduled by string name. The step list is data, so no new Workflow code is needed for a new ordering.

Replay-safe

The catalog reaches the Workflow only through an Activity result, so a catalog change cannot change the replay of a run already in flight.

Typed failures

Each step has its own timeout and retry policy. Bad input is non-retryable, so the run fails after one attempt.

Dispatch2 / 5

Steps are Activity types named at run time

ExecuteActivity accepts a function reference or a string. This Workflow uses both, and the difference determines what the SDK can check before a step runs.

workflow/workflow.go
// Validation is fixed: by reference, so the SDK
// checks the name and argument types.
workflow.ExecuteActivity(validateCtx,
    activities.ValidateRequest, req)

// Steps come from the request: by string name.
for i, def := range plan.Steps {
    name := def.Name
    stepCtx := workflow.WithActivityOptions(ctx,
        activityOptions(def))
    workflow.ExecuteActivity(stepCtx, name, inputs).
        Get(stepCtx, &outputs)
    for k, v := range outputs { bag[k] = v }
}

Every step has the same signature, func(ctx, map[string]string) (map[string]string, error), so one call site can dispatch any of them. The shared data bag carries each step's outputs to the steps after it.

An unregistered name fails late

If a step is added to catalog.go without a matching method, the worker can't find the Activity type. The failure is retryable, so the step uses all three attempts before the Workflow fails.

Outputs aren't checked

Whatever map an Activity returns is merged into the bag. A renamed key doesn't cause an error. Later steps just run degraded.

Determinism & replay3 / 5

Everything the Workflow decides on is in Event History

The data bag, the trace, and the running position are never stored. On replay the Workflow rebuilds them from recorded Activity results, so any worker can pick up a run after a crash.

Event History for the canonical ordering (abridged)
  1. 1WorkflowExecutionStarted Request{steps, data}
  2. ·MarkerRecorded version "validate-request-activity" = 1
  3. ·ActivityTaskScheduled ValidateRequest
  4. ·ActivityTaskCompleted ValidatedRequest{StepDef ×6}
  5. ·ActivityTaskScheduled "LookupAnchorAccount"
  6. ·ActivityTaskCompleted {customer_id, anchor_type, …}
  7. … one scheduled / started / completed group per step …
  8. ·WorkflowExecutionCompleted Result{data, trace, progress}

Workflow Task and ActivityTaskStarted events are omitted.

The catalog arrives as an Activity result

ValidateRequest returns a StepDef snapshot: timeouts, requirements, and confidence inputs. The Workflow reads only that snapshot and never calls into the dsl package, so replay uses the catalog the run was validated against.

A version marker on the first command

GetVersion("validate-request-activity", 1, 1). No execution predates the activity, so min = max = 1, and a history without the marker fails fast instead of drifting. The next change to the command sequence raises the maximum.

Workflow time, not wall time

Elapsed times use workflow.Now. Map iteration appears only where order can't affect a command (copying keys into the bag).

Failure handling4 / 5

Failures are typed, so Temporal knows what's worth retrying

Each step gets Activity options from its own catalog entry. Errors that will recur on every attempt are marked non-retryable, so Temporal fails them on the first attempt.

func activityOptions(def dsl.StepDef) workflow.ActivityOptions {
  return workflow.ActivityOptions{
    StartToCloseTimeout: // declared max + 30s
      time.Duration(def.MaxSeconds)*time.Second +
      30*time.Second,
    RetryPolicy: &temporal.RetryPolicy{
      InitialInterval: time.Second, BackoffCoefficient: 2,
      MaximumInterval: time.Minute, MaximumAttempts: 3,
    },
  }
}

Rejections stay rejected

rejection() re-wraps an InvalidRequest as a non-retryable Workflow error, so a Workflow retry policy added by a caller won't re-run a request that will fail the same way. A validation timeout is still retryable.

No heartbeats

Steps take 20–45s, but there's no HeartbeatTimeout. A dead worker is detected only when StartToClose expires, and a cancellation never reaches a running step.

Visibility & testing5 / 5

Watch the answer build with a Query

A full run takes about a minute. A Query handler shows the running position, confidence, and advisories after each step, without the Workflow sending anything out.

// Registered before the version marker, so progress
// is answerable while validation is still running.
workflow.SetQueryHandler(ctx, "position_progress",
    func() (Progress, error) { return progress, nil })
  • Read-only. A Query adds no events to history, so /api/status can be polled freely.
  • Served by a worker. The state is in memory, so a worker must be polling. With none running, /api/status returns 502.
  • Survives a crash. A worker without the run in cache replays history to rebuild progress before it answers.
  • Works after completion for as long as the namespace retains the run.
